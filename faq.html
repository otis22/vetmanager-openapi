1. Как сопоставить ID счёта и его номер?

Используйте documentNumber. В записи нумерации id — ID самой записи, document_id — ID счёта, document_number — отображаемый номер. ID позиции invoiceDocument.id тоже отличается от ID счёта.

Найти номер по ID счёта (замените 123 ID своего тестового счёта):

curl --get "$VM_URL/rest/api/documentNumber" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'filter=[{"property":"document_type","value":"invoice","operator":"="},{"property":"document_id","value":123,"operator":"="}]'

Обратный поиск по полному номеру, включая префиксы и разделители:

curl --get "$VM_URL/rest/api/documentNumber" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'filter=[{"property":"document_type","value":"invoice","operator":"="},{"property":"document_number","value":"INV-000123","operator":"="}]'

В data.documentNumber ищите соответствующую запись. Пустой список означает отсутствие совпадения. Номер зависит от настроек нумерации; не считайте его глобально уникальным. При нумерации по филиалам уточняйте поиск по clinic_id; при общей нумерации он равен 0, поэтому не добавляйте филиал счёта в фильтр автоматически. Чтение API не создаёт отсутствующий номер. Настройка складской нумерации не определяет нумерацию счетов.

2. Есть ли API Лаборатории?

Пилотный проект

Интеграция с лабораторией доступна в рамках пилотного проекта. Обратитесь к своему провайдеру лаборатории и попросите включить клинику в пилот. Заявку на подключение подаёт провайдер.

Provider API использует отдельный доступ и документацию провайдера. Обычный REST-ключ не предоставляет универсальное управление лабораторными заявками. Чтение результатов в медицинских картах — отдельная операция; оно не заменяет создание и обработку заявок.

Для чтения результатов смотрите GET /rest/api/medicalCards/laboratoryResults и обязательные параметры в Swagger.

3. Есть ли API задач и плановых звонков?

На тестировании (в разработке) · BT-14531

Новая возможность ещё проходит тестирование. Доступность в рабочей версии уточняйте перед использованием.

POST /rest/api/userCalls предназначен для создания задач. Создание звонков в эту доработку не входит, несмотря на название метода.

Ниже — примеры контракта на тестировании. Подставьте существующие ID питомца и сотрудников тестовой клиники. Дата dt передаётся без времени. Укажите ровно одного исполнителя: сотрудника (user_id) или группу (position_id).

curl "$VM_URL/rest/api/userCalls" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  -H 'Content-Type: application/json' \
  --data '{"type":"task","dt":"2026-12-15","pet_id":123,"creator_id":10,"user_id":11,"note":"Контроль самочувствия"}'

Задача на группу:

curl "$VM_URL/rest/api/userCalls" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  -H 'Content-Type: application/json' \
  --data '{"type":"task","dt":"2026-12-15","pet_id":123,"creator_id":10,"position_id":2,"note":"Связаться с владельцем"}'

Ожидаемый результат нового контракта — HTTP 201 и созданная задача; некорректные поля и ссылки отклоняются с HTTP 406. Примечание — до 250 символов, обязательно при соответствующей настройке клиники. Статус и дату создания задаёт сервер. Создание без питомца, выполнение, перенос и отмена задач этой доработкой не описываются. Итоговый контракт, включая поле type, уточняется по результатам тестирования.

4. Как получить тестовый доступ?

При создании домена клинике предоставляется пробный период на две недели. За тестовым доменом, условиями продления и стоимостью обратитесь в поддержку VetManager. Рабочий домен клиники и тестовый домен — разные окружения.

После выдачи домена включите REST-интеграцию и получите ключ. Проверить подключение можно запросом списка с одной записью:

curl --get "$VM_URL/rest/api/client" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'limit=1'

Проверьте HTTP-код и поле success. Пустой список при успешном ответе допустим. Этот запрос проверяет доступ к уже выданному домену, а не создаёт тестовое окружение.

5. Как получить цены по филиалам?

Читайте goodSaleParam с фильтрами по товару good_id и филиалу clinic_id. У одного товара может быть несколько параметров продажи: учитывайте единицу продажи unit_sale_id, коэффициент coefficient и способ формирования цены price_formation.

curl --get "$VM_URL/rest/api/goodSaleParam" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'filter=[{"property":"good_id","value":123,"operator":"="},{"property":"clinic_id","value":1,"operator":"="}]'

В data.goodSaleParam возвращаются совпавшие параметры и их price. Пустой результат не означает нулевую цену и не выбирает автоматически цену другого филиала. Цена параметра продажи отличается от исторической суммы позиции счёта.

6. Чем отличаются REST-ключ и сервисный ключ?

REST-ключ выдаётся для клиники; REST-интеграция должна быть включена. Передавайте его в заголовке X-REST-API-KEY. Ключ не подставляет автоматически сотрудника в поля автора или исполнителя.

curl --get "$VM_URL/rest/api/client" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'limit=1'

Сервисный доступ подключается отдельно для интеграции. Используются заголовки X-SERVICE-NAME и X-SERVICE-REST-API-KEY; конкретные методы и доступ клиники согласуются при подключении. Это не взаимозаменяемые ключи. Provider API лабораторий также имеет отдельный порядок подключения.

curl --get "$VM_URL/rest/api/client" \
  -H "X-SERVICE-NAME: $VM_SERVICE_NAME" \
  -H "X-SERVICE-REST-API-KEY: $VM_SERVICE_KEY" \
  --data-urlencode 'limit=1'

Сервисный пример применим только после подключения и разрешения этого метода. При ошибке доступа проверьте домен, вид ключа, включение интеграции и разрешения. Не публикуйте ключи в URL или переписке.

7. Почему возвращается только 100 записей?

По умолчанию стандартный список возвращает до 100 записей. Параметр limit задаёт размер страницы и может быть больше 100. Например, limit=500 вернёт до 500 записей, если столько записей соответствует запросу.

Первая страница с размером 100 записей и смещением offset=0.

curl --get "$VM_URL/rest/api/client" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'limit=100' \
  --data-urlencode 'offset=0' \
  --data-urlencode 'sort=[{"property":"id","direction":"ASC"}]'

Для второй страницы offset=100 пропускает первые 100 записей. Размер страницы, фильтр и сортировка остаются теми же.

curl --get "$VM_URL/rest/api/client" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'limit=100' \
  --data-urlencode 'offset=100' \
  --data-urlencode 'sort=[{"property":"id","direction":"ASC"}]'

Для каждой следующей страницы увеличивайте offset на limit. Записи находятся в data.client, а общее число совпадений в data.totalCount. Остановитесь, когда достигнете общего числа записей или получите пустую страницу. Если между запросами записи добавляются или удаляются, возможны пропуски и повторы.

8. Как определить позиции комбинации в счёте?

В invoiceDocument поле document_id содержит ID счёта. Для нешаблонной комбинации tag_id содержит ID комбинации. Поле good.for_combination описывает товар в каталоге.

Получите позиции счёта с ID 123.

curl --get "$VM_URL/rest/api/invoiceDocument" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'filter=[{"property":"document_id","value":123,"operator":"="}]'

Пример ответа с полями, нужными для группировки.

{
  "success": true,
  "data": {
    "totalCount": 4,
    "invoiceDocument": [
      {"id": 701, "document_id": 123, "good_id": 308, "tag_id": 42},
      {"id": 702, "document_id": 123, "good_id": 309, "tag_id": 42},
      {"id": 703, "document_id": 123, "good_id": 315, "tag_id": 0},
      {"id": 704, "document_id": 123, "good_id": 316, "tag_id": 0}
    ]
  }
}

Позиции 701 и 702 относятся к комбинации 42. При группировке внутри счёта объединяйте строки с одинаковым tag_id больше нуля.

Позиции 703 и 704 оставьте отдельными строками. tag_id=0 встречается и у товаров, добавленных по отдельности, и у компонентов шаблонной комбинации. По нулю нельзя определить, как эти позиции попали в счёт.

Поле price содержит сумму всей строки за указанное количество.

9. Как получить файлы клиента или питомца?

Различайте прикреплённые файлы и ссылки внутри HTML медицинской карты. Для чтения конкретной карты используйте её ID:

curl --get "$VM_URL/rest/api/MedicalCards/123" \
  -H "X-REST-API-KEY: $VM_API_KEY"

В data ищите HTML-содержимое карты и ссылки на вложения. Извлечение ссылок из HTML — обходной путь: это не отдельный универсальный API списка файлов клиента или питомца. Доступность найденной ссылки и требования авторизации проверяются отдельно. Не отображайте полученный HTML без безопасной обработки.

MedicalCards/UploadFiles служит для загрузки файлов и не заменяет их чтение. Возможность получить произвольное вложение карточки клиента этим методом не заявляется.

10. Как правильно передать filter и sort?

Оба параметра стандартного списка — JSON-массивы, переданные как строки. Условия filter объединяются через AND и относятся к столбцам самой модели; вложенные пути связей не поддерживаются. Для GET кодируйте их с помощью --data-urlencode.

curl --get "$VM_URL/rest/api/client" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'filter=[{"property":"id","value":[1,2,3],"operator":"in"}]' \  --data-urlencode 'sort=[{"property":"id","direction":"DESC"}]' \  --data-urlencode 'limit=100'

Операторы: =, !=, <>, <, <=, >, >=, in, not in, like. Для in и not in значение — массив. Направления сортировки — ASC и DESC. Например, диапазон дат медицинских карт:

curl --get "$VM_URL/rest/api/MedicalCards" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'filter=[{"property":"date_create","value":"2026-11-01 00:00:00","operator":">="},{"property":"date_create","value":"2026-12-01 00:00:00","operator":"<"}]'

Для длинного фильтра стандартного списка используйте POST на /{controller}/list с полями формы:

curl "$VM_URL/rest/api/client/list" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'filter=[{"property":"id","value":[1,2,3],"operator":"in"}]' \
  --data-urlencode 'sort=[{"property":"id","direction":"ASC"}]' \
  --data-urlencode 'limit=100'

Это чтение списка, не создание клиента. Тело имеет формат application/x-www-form-urlencoded, а не JSON. Не дублируйте параметры одновременно в URL и теле. Пользовательские действия могут иметь иной контракт.

11. Почему не приходят вебхуки?

  1. Проверьте, что сервис вебхуков активен, URL указан точно, а нужное событие включено в подписку.
  2. Посмотрите историю ошибок для этого URL.
  3. Устраните сетевую ошибку или ошибку приёмника. Приёмник должен ответить за 5 секунд кодом 200–206; перенаправление считается ошибкой.
  4. Если сервис отключён, включите его в справочнике после исправления причины. Учтите возможную оставшуюся временную паузу.
  5. Создайте новое подходящее событие в тестовой клинике и проверьте реальную доставку.
curl --get "$VM_URL/rest/api/failedHook" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  --data-urlencode 'filter=[{"property":"hook_url","value":"https://example.test/hooks/vetmanager","operator":"="}]' \  --data-urlencode 'sort=[{"property":"id","direction":"DESC"}]' \  --data-urlencode 'limit=20'

Диагностика доступна при разрешённом доступе к методу. Вебхук приходит POST-запросом application/x-www-form-urlencoded: поля name, data[…], params[…]. JSON в теле ответа приёмника не анализируется: HTTP 200 с success=false всё равно считается доставкой.

Паузы, отключение и восстановление

С третьей учтённой ошибки начинается пауза: 5, 10, 20, 40, затем до 60 минут. После её истечения отправка пробуется на новом событии. Успех сбрасывает счётчик и паузу, но не удаляет историю ошибок.

История считается по точному URL. Если перед очередной неудачной отправкой уже сохранено 1000 ошибок, сервис отключается. У сервисов с одним URL история общая, временная пауза — своя.

Включение через справочник очищает историю выбранного URL, но не сбрасывает временную паузу. Удаление строк failedHook не включает сервис и не переотправляет события. Во время паузы события пропускаются; автоматического воспроизведения пропущенных событий нет.

Пробный curl к приёмнику проверяет только сам приёмник. Для проверки всей цепочки нужно настоящее событие VetManager.

12. Как работают status и confirmation у Admission?

status — состояние приёма в расписании, а confirmation — отдельный результат ответа клиента. Эти поля нельзя подменять друг другом.

Значения status
ЗначениеСмысл
saveЗапланирован
directedКлиент направлен на приём
in_treatmentПриём начат
acceptedЗавершён
deletedУдалён
delayedПросрочен
not_approvedНе одобрен
not_confirmedНе подтверждён
Значения confirmation
ЗначениеОтвет клиента
confirmedПодтвердил
cancelledОтменил
postponedПеренёс
Пустая строка / nullОтвет не указан
curl --get "$VM_URL/rest/api/admission/123" \
  -H "X-REST-API-KEY: $VM_API_KEY"

При создании приём получает status=not_confirmed. Действие confirmAdmission подтверждает запись в расписании: устанавливает save либо not_approved при непрохождении проверки. Оно не устанавливает confirmation=confirmed.

Пример подтверждения тестового приёма (все ID и дату замените значениями этой записи):

curl "$VM_URL/rest/api/admission/confirmAdmission" \
  -H "X-REST-API-KEY: $VM_API_KEY" \
  -H 'Content-Type: application/json' \
  --data '{"id":123,"user_id":10,"client_id":20,"patient_id":30,"admission_date":"2026-12-15 10:00:00","admission_type":1,"clinic_id":1}'

Проверяйте success даже при HTTP 201, затем повторно прочитайте приём. При переносе через PUT передавайте start и end по контракту метода. Значение confirmation=cancelled само по себе не заменяет операцию отмены приёма. Время согласуйте с часовым поясом клиники.
