# BT-14577. Предпросмотр и синхронизация OpenAPI

## К чему пришли

Публичный контракт хранится в `vetmanager-openapi`. Источник документации — существующие YAML и JSON, включая уже внесённые вручную изменения. Утилиты сверки и генерации находятся в этом же репозитории. `vetmanager-extjs` предоставляется как локальный checkout, из которого читается выбранный Git-коммит. Отдельные файлы контрактов и изменения CI в бэкенде для этой схемы не требуются.

Маршрут, найденный в PHP, — кандидат для проверки. Перед публикацией нужно подтвердить публичность операции и её контракт. Путь и HTTP-метод можно сопоставить по коду. Параметры, обязательные поля, ответы и права доступа проверяются по реализации и HTTP-сценариям.

## 1. Ручной предпросмотр

Из корня `vetmanager-openapi` запустите:

```bash
python3 scripts/preview_sync.py HEAD
python3 scripts/preview_sync.py feature/BT-14451-15477-15559 --compare-to origin/develop
python3 scripts/preview_sync.py cd0759faf4
```

Нужны Git, Python 3.12 или новее и PyYAML. `HEAD` означает текущий коммит соседнего `vetmanager-extjs`. Вместо него можно передать любую локально доступную ветку, тег или SHA. Параметр `--extjs-root` переопределяет путь к соседнему checkout. Для сравнения по умолчанию используется общий коммит выбранной ревизии и `origin/master`. Через `--compare-to` можно выбрать другую ветку или коммит.

Скрипт читает текущие YAML и JSON из рабочей копии OpenAPI, включая согласованные локальные правки в обоих файлах. Бэкенд читается из коммита, поэтому для просмотра другой ветки переключать checkout не требуется. По умолчанию предпросмотр работает офлайн и сверяет статические маршруты.

При офлайн-запуске скрипт печатает пути к двум файлам во временном каталоге. Чтобы указать свой новый каталог, передайте `--output /path/to/new-directory`.

- `openapi.diff` показывает изменения, которые предложил текущий скрипт сверки. Сравнение представлено в JSON. Результаты сопоставления находятся в отчёте, а в diff попадают изменения самой спецификации, включая предложенную нормализацию. Порядок ключей, служебные метаданные и время запуска не создают шум в diff.
- `review.md` показывает добавленные и исчезнувшие маршруты относительно базы, изменённые REST-файлы, вероятно затронутые публичные операции и расхождения со спецификацией. Например, он выделяет операции `createinvoice` и `payinvoice`, даже если их URL сохранились.

Рабочие файлы спецификации остаются на месте. Если `openapi.diff` пуст, всё равно проверьте `review.md`: изменение логики существующего метода может не дать статического diff.

## 2. HTTP-проверки на тестовом стенде

Укажите адрес тестового стенда, развёрнутого из проверяемой ревизии. Для этого режима дополнительно установите `jsonschema` и задайте `VETMANAGER_REST_API_KEY` в окружении. Git-ревизция выбирает код для статической сверки, а HTTP-запросы проверяют версию, которая запущена на указанном стенде.

```bash
python3 -m pip install jsonschema
python3 scripts/preview_sync.py HEAD --api-base-url http://one.localhost:8080
```

Скрипт проверяет `GET` и `POST …/list` для `fiscalRegister`, `fiscalRegisterData` и `invoiceDocument`. Он сверяет статус и JSON со схемой, сравнивает ответы GET и POST с одинаковыми полями, проверяет POST без тела и два документированных отказа. В `http-checks.md` сохраняются результаты, число записей и места расхождений со схемой. Если список пуст, проверяется только оболочка ответа. Для проверки полей записей на стенде должны быть тестовые данные. При несовпадении команда возвращает код 1.

## 3. Применение подтверждённых изменений

1. Расширить предпросмотр генерацией стандартных операций по общим шаблонам. Например, утверждённый публичный `POST …/list` может использовать форму фильтрации и схему ответа соответствующего `GET`.
2. Для нестандартных методов использовать существующую спецификацию и точечно обновлять в ней затронутые параметры, схемы и ответы. Предпросмотр должен показывать, какие изменения подтверждены и какие требуют проверки.
3. Расширить HTTP-проверки на изменённые публичные методы. Для `createinvoice` и `payinvoice` подготовить тестовые данные и сценарии успешного запроса, валидации и отказа в доступе.
4. Согласованные изменения коммитить в `vetmanager-openapi` в обоих форматах и запускать существующий валидатор.

## 4. Автоматический запуск после ручного этапа

1. Настроить отдельный процесс с доступом к приватному GitLab для чтения свежего SHA `vetmanager-extjs/master`. Утилита и настройки синхронизации остаются в проекте OpenAPI.
2. Запускать сравнение с последней обработанной ревизией. Передавать на публичную сторону только проверенный diff OpenAPI и пригодную для публикации сводку.
3. При изменении публичной спецификации создавать или обновлять один PR. После ручного merge существующая сборка GitHub Pages публикует Swagger.
4. Проверить повторный прогон, ошибку чтения снимка, отсутствие изменений, изменение существующего метода и появление нового метода.
